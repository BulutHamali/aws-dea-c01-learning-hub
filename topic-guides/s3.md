# Amazon S3 lifecycle, replication, and lake storage

[Topic index](README.md) · [Home](../README.md)

## The idea

S3 stores data objects under keys. Use the key layout to make the stages of the pipeline visible, such as raw/, curated/, and quarantine/.

## How to decide

| Concept | When it matters |
|---|---|
| **Storage class** | Choose using access frequency, retrieval deadline, and total cost. Include retrieval charges and minimum storage durations. |
| **Lifecycle** | Transition or expire objects based on rules. In versioned buckets, plan current and noncurrent versions separately. |
| **Replication** | Copy objects to another bucket, including across Regions with CRR. Use Batch Replication for eligible existing objects. |
| **Transfer Acceleration** | Improve transfers to or from an enabled bucket over long distances. Replication addresses the separate need for a second copy. |

## Common mistake

When a policy says to retain data for 15 years, include a retrieval deadline and address retention controls if deletion must be prevented. A transition rule alone changes storage class.

## Try it

A research archive is actively queried for five years, then retained for ten more years with a two-day retrieval window.

<details>
<summary>Show the reasoning</summary>

Keep the queryable years in a class that fits the active access pattern. Evaluate Deep Archive for the later years, confirm retrieval and retention requirements, and configure expiration only where policy allows.
