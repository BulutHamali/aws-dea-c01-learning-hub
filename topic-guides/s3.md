# Amazon S3 storage classes, lifecycle, retention, and recovery

[Topic index](README.md) · [Exam map](../EXAM-MAP.md)

## The idea

Amazon Simple Storage Service (Amazon S3) stores objects under keys in buckets. In a data lake, the key layout makes each pipeline stage visible: `raw/`, `curated/`, and `quarantine/`. Three separate questions decide how you store those objects:

1. **How often is the data read, and how fast must it come back?** That picks the storage class.
2. **When should it move or disappear?** That is a lifecycle rule.
3. **Must nobody be able to delete it?** That is a retention control, and lifecycle cannot provide it.

## Storage classes, retrieval, and lifecycle rules

| Storage class | Pick it when | Watch out for |
|---|---|---|
| S3 Standard | Data is read often or by unpredictable jobs | Highest storage price of the general classes |
| S3 Intelligent-Tiering | Access patterns are unknown or change over time | Objects under 128 KB are not monitored and stay in the Frequent Access tier |
| S3 Standard-IA | Read rarely, but needs millisecond access when read | Per-GB retrieval fee, 30-day minimum, 128 KB minimum billable size |
| S3 One Zone-IA | Rarely read data you can re-create if one Availability Zone is lost | Stored in a single Availability Zone |
| S3 Glacier Instant Retrieval | Archive data that still needs millisecond reads, about once a quarter | 90-day minimum, 128 KB minimum billable size |
| S3 Glacier Flexible Retrieval | Archive data where minutes to hours is acceptable | Must be restored before reading. 90-day minimum |
| S3 Glacier Deep Archive | Long-term records where hours to two days is acceptable | Must be restored before reading. 180-day minimum |
| S3 Express One Zone | Single-digit millisecond access for latency-sensitive jobs in one Availability Zone | Uses directory buckets in one zone |

A **lifecycle rule** transitions or expires objects by age, prefix, tag, or object size. Transitions only go "down" the waterfall. For example, Glacier Flexible Retrieval can move only to Deep Archive, and nothing moves out of Deep Archive by lifecycle. A rule cannot skip a class's minimum duration. If you move objects early, you pay for the rest of the minimum period.

### Worked example

The lab queries sequencing metrics actively for five years, then must keep them ten more years. Auditors accept a two-day turnaround on old data.

- Years 0 to 5: S3 Standard, or Intelligent-Tiering if access fades unevenly.
- Year 5 onward: a lifecycle transition to Glacier Deep Archive. A bulk restore fits a two-day window.
- Year 15: an expiration action, only if policy allows deletion at that point.
- If the regulation says records must not be deleted early by anyone, add S3 Object Lock. The transition rule alone does not stop a delete.

## Expiration rules for current and older versions

In an unversioned bucket, an expiration action deletes the object. In a **versioned** bucket, the same action adds a delete marker and keeps the previous version as a *noncurrent* version. Plan two kinds of rules:

- **Current version actions** transition or expire the version people normally read.
- **Noncurrent version actions** transition or permanently delete older versions after a number of days. You can also keep a set number of newer noncurrent versions.

Add a rule to clean up incomplete multipart uploads and expired delete markers, or storage grows silently.

## Versioned deletes and DynamoDB TTL comparison

| Need | S3 | DynamoDB |
|---|---|---|
| Undo an accidental overwrite or delete | Turn on versioning and restore the previous version | Point-in-time recovery restores the table to a new table |
| Remove data automatically after an age | Lifecycle expiration | Time to Live (TTL) on a per-item timestamp attribute |
| Timing of the automatic delete | Asynchronous after the rule's age is reached | Typically within a few days of expiry. Expired items can still appear in reads, so filter them |
| Cost of the automatic delete | No request charge for lifecycle expiration | TTL deletes do not consume write capacity in the table's Region |

See [database selection](databases.md) for TTL details.

## Deletion, Object Lock, and legal holds

**S3 Object Lock** stores object versions in a write-once-read-many (WORM) model. It requires versioning.

| Control | What it does | Who can override |
|---|---|---|
| Governance mode | Blocks deletes and overwrites of a locked version until the retain-until date | Users with `s3:BypassGovernanceRetention` who send the bypass header |
| Compliance mode | Blocks deletes and overwrites by every user, including the root user. The period cannot be shortened | Nobody. Only deleting the account removes it early |
| Legal hold | Same protection with no end date, until someone removes the hold | Users with `s3:PutObjectLegalHold` |

A lock protects a specific version. Clients can still add new versions and delete markers on top. Readers then see the delete marker, while the locked version remains recoverable.

## Replication, version recovery, and restore testing

| Need | Feature | Key condition |
|---|---|---|
| Copy new objects to another bucket, same or other Region | Same-Region (SRR) or Cross-Region Replication (CRR) | Versioning on source and destination. An IAM role S3 can assume |
| Copy objects that existed before the rule | S3 Batch Replication | Run as a Batch Operations job |
| Predictable replication time for compliance | S3 Replication Time Control (RTC) | Most objects in seconds, 99.9% within 15 minutes, with exclusions |
| Faster long-distance uploads | S3 Transfer Acceleration | Speeds transfers into one bucket. It does not create a second copy |

Replication is not a backup by itself. Deletes with version IDs are not replicated by default, but a bad overwrite is replicated as a new version. Test recovery by restoring a version and, for Glacier classes, timing a restore.

## Common mistake

"Keep for seven years" and "prevent deletion for seven years" are different requirements. Lifecycle handles the first. Object Lock in compliance mode handles the second.

## Commonly confused

| Choices | Deciding requirement |
|---|---|
| Intelligent-Tiering vs. Standard-IA | Unknown or changing access favors Intelligent-Tiering. A known rare-access pattern favors Standard-IA |
| Glacier Instant vs. Flexible vs. Deep Archive | Milliseconds, minutes to hours, or hours to two days |
| Lifecycle expiration vs. Object Lock | Lifecycle deletes on schedule. Object Lock prevents deletion |
| Governance vs. compliance mode | Can a privileged admin override? Governance yes, compliance no |
| Replication vs. Transfer Acceleration | A second copy vs. faster transfer into one bucket |

**Exam cues:** "WORM", "regulator", "even the root user" → Object Lock compliance mode. "Unpredictable access" → Intelligent-Tiering. "Within 15 minutes" replication → RTC. "Existing objects" replication → Batch Replication.
